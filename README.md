## 2. Известные грабли

Без изменений с прошлой версии: `verbatimModuleSyntax` требует
type-only импорты; CORS между портами в dev требует `cors()` на
сервере.

**Новое — цепочка багов при переходе на httpOnly cookie** (все три
реально воспроизведены и по итогу устранены):

1. **Токен в `localStorage` стал бесполезен** — httpOnly cookie не
   читается из JS в принципе, это и есть весь смысл флага `httpOnly`.
   Решение: клиент больше не хранит и не читает токен сам, полагается
   на то, что браузер сам приложит cookie к каждому запросу
   (`withCredentials: true` + `cors({ credentials: true, origin: <конкретный> })`
   на сервере — с `credentials: true` origin не может быть `*`).

2. **Бесконечная перезагрузка страницы на экране авторизации.**
   Причина — глобальный response-интерцептор в `api/client.ts`
   изначально трактовал **любой** `401` как признак протухшей сессии
   и делал `window.location.href = "/login"`. Но при старте приложения
   `AuthContext` специально дёргает защищённый эндпоинт, чтобы понять,
   валидна ли cookie (JS не может проверить это иначе) — и для
   неавторизованного пользователя такой запрос **ожидаемо** возвращает
   `401`. Интерцептор это не различал → редирект → `AuthContext`
   монтируется заново → снова `401` → снова редирект → бесконечный
   цикл. Исправлено добавлением проверяемого эндпоинта в список
   исключений интерцептора (`AUTH_ENDPOINTS`).

3. **Тот же цикл не прекратился после первого фикса** — оказалось,
   `api/client.ts` поправили, а `api/auth.ts` — нет: функция `me()`
   всё ещё дёргала старый `/api/test-auth` (изначально заведённый
   как личный отладочный эндпоинт, не для прода), которого не было в
   списке исключений. Нашли по скриншоту Network-панели (запросы
   `test-auth`, а не `me`). Решение — на сервере завели полноценный
   `GET /api/users/me` под тем же `authMiddleware`, клиент переключили
   на него.

**Урок на будущее (озвучен в чате):** при auth-логике на cookie
список исключений интерцептора (`client.ts`) и реальный URL вызова
(`auth.ts`) — два независимых места, которые должны обновляться
синхронно. Разъехались один раз — получили цикл перезагрузок.

## 4. Слой работы с API

### `api/client.ts`

- `apiClient = axios.create({ baseURL: VITE_API_URL, withCredentials: true })`
- Токен в заголовки **не подставляется** — авторизация целиком через
  cookie, которую браузер прикладывает сам
- Response-интерцептор: на `401` — `window.location.href = "/login"`,
  **кроме** запросов из `AUTH_ENDPOINTS`:
  `/users/login`, `/users/register`, `/users/verify`, `/users/me`

> Подтверждено реальным тестированием: интерцептор больше не вызывает
> цикл перезагрузок на `/users/me` после того, как оба места
> (`client.ts` и `auth.ts`) синхронизировали список/эндпоинт.

### `api/auth.ts`

- **`register(email, password): Promise<{ message, email }>`** — `POST /users/register`
- **`verifyEmail(email, code): Promise<{ user, token }>`** — `POST /users/verify`.
  Поле `token` в ответе сервер всё ещё возвращает, клиент его больше
  не использует
- **`login(email, password): Promise<{ user, token }>`** — `POST /users/login`, аналогично не использует `token`
- **`logout(): Promise<...>`** — `POST /users/logout`, чистит cookie на сервере
- **`me(): Promise<{ user }>`** — `GET /users/me`. Используется
  `AuthContext` при старте приложения для проверки валидности cookie
  (замена личного отладочного `/test-auth`, который для этой роли не
  предназначался)

## 5. Реализованные компоненты и хуки

- **`AuthContext` / `useAuth()`**
  Состояние: `user`, `isAuthenticated` (`!!user`), `isLoading`. При
  монтировании вызывает `authApi.me()` — если cookie валидна,
  `setUser(data.user)`, иначе `setUser(null)`; в обоих случаях
  `isLoading` становится `false` по завершении. `setSession(user)` —
  вызывается после `login`/`verify` (токен больше не принимает, только
  пользователя). `logout()` — асинхронный: сперва `authApi.logout()`
  (чистит cookie на сервере), затем `setUser(null)`.
  **Подтверждено:** проверка сессии при старте реально работает —
  устранённый цикл перезагрузок был прямым следствием этой логики.

- **`ProtectedRoute`** — при `isLoading` показывает плейсхолдер
  "Загрузка...", иначе `<Outlet />` если авторизован, иначе `<Navigate to="/login" />`
  (либо всегда `<Outlet />`, если включён dev-флаг `VITE_SKIP_AUTH`).
  Применение после перехода на cookie не подтверждено отдельно —
  файл обновлён в комплекте с остальными, отдельно не тестировался.

- **`AuthPage`** — при `isLoading` не рендерит ничего; если уже
  авторизован — `<Navigate to="/posts" replace />`; иначе табы
  Вход/Регистрация. **Частично подтверждено**: то, что форма логина
  корректно показывается неавторизованному пользователю после
  исчезновения цикла — да; поведение при реальной авторизации отдельно
  не подтверждено.

- **`LoginForm`**, **`RegisterForm`** — без изменений в форме, кроме
  `setSession(user)` вместо `setSession(user, token)` в `LoginForm`.
  Само успешное прохождение логина после перехода на cookie отдельно
  не подтверждено.

- **`useTheme()`**, **`AppLayout`** — без изменений с прошлой версии
  (light/dark, шапка с навигацией/email/выходом). `AppLayout` теперь
  вызывает `logout()` асинхронно и затем `navigate("/login", { replace: true })`.
  Не подтверждено отдельным тестированием.

Без изменений с прошлой версии (форма отделена от страницы, сессия
только через `useAuth()`, ошибки маппятся в компоненте формы,

  любая новая логика, которой раньше был бы нужен токен из
  `localStorage`, должна просто полагаться на `withCredentials: true`
  и cookie
- **Любой новый защищённый эндпоинт, который может законно вернуть
  `401` не как признак разрыва сессии** (по аналогии с `/users/me`),
  нужно сразу заносить в `AUTH_ENDPOINTS` в `client.ts` — и убедиться,
  что `api/auth.ts` (или другой вызывающий файл) реально обращается по
  тому же пути, что указан в этом списке

## 9. Открытые технические решения

- **`sameSite: "strict"`** у cookie на сервере — для dev (`localhost`,
  разные порты) работает, т.к. `SameSite` сравнивает домен, а не порт.
  Когда фронт и бэк в проде окажутся на разных доменах (не поддоменах
  одного домена) — `strict` заблокирует отправку cookie при обычных
  кросс-доменных запросах. Домен фронта в проде всё ещё не определён —
  вопрос не решён.
- **Формат тела ошибки** от `/users/register` и `/users/login` не
  подтверждён — маппинг в `ERROR_MESSAGES` сделан по HTTP-статусу
  "вслепую".
- **Библиотека иконок** не выбрана — эмодзи как заглушка.

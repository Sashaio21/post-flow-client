# PROJECT CONTEXT: post-flow (клиент)

Последнее обновление: 2026-07-29

Справка для восстановления контекста без чтения всего кода. Строго
разделяет "реально в проекте" (подтверждено чтением реального архива
клиента) и "обсуждалось/предлагалось в чате, но не применено" — не

был прислан и прочитан целиком — предыдущая версия строилась по

Расхождений с прошлой версией по auth-логике не нашлось, она
подтверждена как есть. Основные изменения этой сессии: реализован
`api/posts.ts` (был пустым файлом-заглушкой), написана страница
`PostsPage` со списком постов, добавлен слой `components/` и цветовая
тема на основе присланного UI-прототипа.

## 2. Известные грабли

Без изменений с прошлой версии:

- `verbatimModuleSyntax` требует type-only импорты (`import { type Foo }`)
- CORS между портами в dev требует `cors({ credentials: true, origin: <конкретный> })`
  на сервере — с `credentials: true` origin не может быть `*`
- `withCredentials: true` в axios обязателен для отправки/приёма
  httpOnly cookie между `localhost:5173` и `localhost:3000`

Новых граблей по тулингу в этой сессии не встретилось.

## 4. Слой работы с API

### `api/client.ts` — без изменений с прошлой версии

- `apiClient = axios.create({ baseURL: VITE_API_URL, withCredentials: true })`
- Интерцептор 401 → `window.location.href = "/login"`, кроме
  `AUTH_ENDPOINTS = ["/users/login", "/users/register", "/users/verify", "/users/me"]`

### `api/auth.ts` — без изменений с прошлой версии

- **`register(email, password): Promise<{ message, email }>`** — `POST /users/register`
- **`verifyEmail(email, code): Promise<{ user, token }>`** — `POST /users/verify`. Возвращённый `token` клиентом не используется
- **`login(email, password): Promise<{ user, token }>`** — `POST /users/login`, `token` аналогично не используется
- **`logout(): Promise<...>`** — `POST /users/logout`
- **`me(): Promise<{ user }>`** — `GET /users/me`, используется `AuthContext` при старте

### `api/posts.ts` — НОВОЕ, реализовано в этой сессии

- **`postsApi.list(): Promise<Post[]>`** — `GET /posts` (с учётом `baseURL` это `/api/posts`
  на сервере). Возвращает посты текущего пользователя. Побочных эффектов на клиенте нет.

Тип `Post` (объявлен в этом же файле) списан с реальной Prisma-модели
сервера: `id, title, status, socialNetwork, scheduledAt, tags, images,
templateId, authorId, createdAt, updatedAt`.

> **Сверка с серверной PROJECT CONTEXT:** `GET /api/posts` там
> подтверждён как реализованный и рабочий эндпоинт — расхождений нет.
> Методы `create/update/delete` на клиенте пока не написаны (сервер их
> уже отдаёт: `POST/PUT/DELETE /api/posts/:id`), т.к. страница
> создания/редактирования поста сознательно не делалась — см. раздел 9.

### `api/socialConnections.ts` — пустой, без функций

## 5. Реализованные компоненты и хуки

- **`AuthContext` / `useAuth()`** — без изменений с прошлой версии.
  `user`, `isAuthenticated`, `isLoading`; при монтировании дёргает
  `authApi.me()`; `setSession(user)` после login/verify; `logout()`
  асинхронный.

- **`ProtectedRoute`** — без изменений в логике (`VITE_SKIP_AUTH`,
  плейсхолдер "Загрузка...", редирект на `/login`).
  **Мелкая неточность:** комментарий в коде всё ещё гласит "Пока идёт
  запрос /test-auth (проверка cookie)" — реально запрос идёт через
  `authApi.me()` → `/users/me`. На поведение не влияет, но комментарий
  вводит в заблуждение при чтении кода.

- **`AuthPage`, `LoginForm`, `RegisterForm`, `VerifyEmailPage`** — без
  изменений в логике. Уточнение: `LoginForm` при `403` (email не
  подтверждён) сам редиректит на `/verify?email=...`, не просто
  показывает ошибку.

- **`useTheme()`** — без изменений: `light`/`dark`, хранится в
  `localStorage`, переключает класс `dark` на `<html>`.

- **`AppLayout`** — логика выхода не менялась. **Визуально
  перекрашен** в новые цветовые токены (`bg-bg`, `text-fg`,
  `border-line`, `bg-surface-2` и т.д.) вместо хардкод-серого
  Tailwind-палитры, чтобы совпадать со стилем `PostsPage`.

- **`components/posts/postDisplay.ts`** — не компонент, общий модуль:
  `platformLabel`, `platformChipClass`, `statusLabel`, `statusDotClass`,
  `formatScheduledAt()`. Вынесен, т.к. используется одновременно в
  `PostsPage`, `UpcomingStrip` и `PostsFilterBar`.

- **`components/posts/UpcomingStrip`** — чисто презентационный:
  принимает готовый (уже отфильтрованный/отсортированный/обрезанный до 4) список постов и рендерит горизонтальную ленту "Ближайшие
  публикации". Никакой логики выборки внутри не содержит — она в
  `PostsPage`.

- **`components/posts/PostsFilterBar`** — полностью controlled:
  `search`, `platform`, `status` + колбэки `onChange`, никакого
  внутреннего состояния.

## 6. Маршруты (роутинг)

Без изменений с прошлой версии:

- **`/login`, `/register`** — `AuthPage` (табы), публичный
- **`/verify`** — `VerifyEmailPage`, публичный
- **`/`** — защищённый, редирект на `/posts`
- **`/posts`** — защищённый, `PostsPage`
- **`*`** — редирект на `/`

Вложенность: `ProtectedRoute` → `AppLayout` → страница (`/`, `/posts`
объявлены внутри этой пары вложенных `<Route element={...}>`).

> Маршрут `/posts/new` **не зарегистрирован**. Кнопка "+ Новый пост" на
> `PostsPage` на него ссылается, но т.к. роута нет — сработает catch-all
> `*` и пользователя тихо вернёт на `/posts`. Это осознанная временная
> заглушка, не баг — см. раздел 9.

## 7. Конвенции проекта

Без изменений с прошлой версии (форма отделена от страницы, сессия
только через `useAuth()`, ошибки маппятся в компоненте формы,
Tailwind-классы в JSX, тёмная тема через `dark` class-стратегию,
комментарии на русском, `AUTH_ENDPOINTS` в `client.ts` синхронизируется
вручную с реальными путями в `api/auth.ts`), плюс новое, принятое в
этой сессии:

- **Компонентная архитектура:** `components/<домен>/` — только для
  того, что реально переиспользуется в ≥2 местах (общие подписи,
  форматирование, повторяющиеся куски разметки). Не заводить
  компонент "про запас", если у него пока одно место использования —
  такой код остаётся прямо в странице, пока не появится второе
  применение.
  Внутри домена: presentational-компоненты (`UpcomingStrip`,
  `PostsFilterBar`) не содержат бизнес-логики выборки/сортировки —
  получают готовые данные и колбэки; сама логика (фильтрация,
  `useMemo`) живёт в странице.
- **Цветовая тема:** цвета не хардкодятся Tailwind-палитрой
  (`gray-900` и т.п.), а идут через семантические токены,
  зарегистрированные в `index.css` через `@theme inline` (`bg`,
  `surface`, `surface-2`, `line`, `fg`, `muted`, `scheduled`,
  `published`, `danger`, `tg`, `ig`, `vk` и т.д.), переключаемые между
  `:root` (light) и `.dark`. Источник палитры и шрифтов (Space
  Grotesk/Inter/IBM Plex Mono) — присланный HTML/CSS-прототип.
  **Не мигрировано:** `AuthPage`, `LoginForm`, `RegisterForm`,
  `VerifyEmailPage` всё ещё на старых `gray-*`/`black` классах —
  тема применена пока только к `AppLayout` и `PostsPage` со всем, что
  внутри неё.

## 9. Открытые технические решения

Без изменений с прошлой версии — не переобсуждались в этой сессии:

- `sameSite: "strict"` у cookie в проде на разных доменах — не решено
- Формат тела ошибки от `/users/register` и `/users/login` не
  подтверждён, маппинг в `ERROR_MESSAGES` — по HTTP-статусу вслепую
- Библиотека иконок не выбрана

**Новое:**

- Расхождение модели данных клиент/сервер по контенту поста: в
  UI-прототипе у поста есть `content` (текст/подпись — разный набор
  полей на платформу) и отдельные внутренние `tags` для доски
  (не путать с хэштегами внутри `content`). В текущей серверной
  `model Post` поля `content` нет вообще — вопрос, как и где его
  добавить (JSON-поле, отдельные колонки на платформу), пока не
  поднимался предметно в клиентском коде, т.к. страница создания/
  редактирования поста ещё не пишется.
